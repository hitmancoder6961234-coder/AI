# Security

## Reporting

Please report vulnerabilities privately to the repository owner (GitHub: *Security -> Report a vulnerability*)

## Studio and document hardening

- Project content is wrapped in `<project_evidence>` and declared to be data: instructions inside uploaded files are
  never followed. Secrets (API keys, tokens, connection strings, private keys, passwords) are scrubbed from the evidence
  before it reaches a model.
- A user-supplied prompt replaces only the style layer; the output contract and the no-invention rules are always
  appended last and cannot be removed.
- Archive extraction is bounded (entry count, total bytes, nesting depth); export never fetches remote URLs.
- Build jobs, their files and downloads are owner-scoped and expire after an hour; limits cap concurrent builds.

## Agent hardening

`fetch_url` resolves and validates the destination **inside the socket's own DNS lookup**, refuses private / loopback /
link-local / CGNAT / multicast and IPv4-embedded IPv6 forms (including `::ffff:7f00:1`), limits ports, re-validates
every redirect and caps size and time. The calculator is a parser, never `eval`. Observations are delimited and declared
untrusted. This reduces - it cannot eliminate - prompt-injection risk: keep agent tools read-only, as they are.

## Content-Security-Policy

Enforced by default (`PRIVACY_CSP=enforce`). One module, `server/security/csp.ts`, builds the policy for both surfaces and sends
it; `vercel.json` carries the identical header for the static host (generated by `scripts/sync-vercel-csp.mjs`, and
`tests/csp.test.ts` fails if the two ever differ).

**Main app** (`/`, `/copilot.html`, `/agent.html`, everything except `/classic`):

```
default-src 'self'; script-src 'self' 'report-sample'; script-src-attr 'none'; style-src 'self' 'report-sample'; style-src-elem 'self' 'report-sample'; style-src-attr 'unsafe-inline'; img-src 'self' data: blob: https://raw.githubusercontent.com https://github.com https://avatars.githubusercontent.com https://user-images.githubusercontent.com https://camo.githubusercontent.com https://img.shields.io https://lh3.googleusercontent.com; font-src 'self' data:; connect-src 'self'; media-src 'self' blob: data:; frame-src 'self' blob:; worker-src 'self' blob:; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'; report-uri /api/csp-report
```

**Classic app** (`/classic/`) is the same policy plus Google Sign-In, limited to the exact paths Google documents:

```
default-src 'self'; script-src 'self' 'report-sample' https://accounts.google.com/gsi/client; script-src-attr 'none'; style-src 'self' https://accounts.google.com/gsi/style 'sha256-RU4sU0AaS8IBGZx8XrGt/pa9A5SLA3dQszGeqT5L3Kw=' 'report-sample'; style-src-elem 'self' https://accounts.google.com/gsi/style 'sha256-RU4sU0AaS8IBGZx8XrGt/pa9A5SLA3dQszGeqT5L3Kw=' 'report-sample'; style-src-attr 'unsafe-inline'; img-src 'self' data: blob: https://raw.githubusercontent.com https://github.com https://avatars.githubusercontent.com https://user-images.githubusercontent.com https://camo.githubusercontent.com https://img.shields.io https://lh3.googleusercontent.com; font-src 'self' data:; connect-src 'self' https://accounts.google.com/gsi/; media-src 'self' blob: data:; frame-src 'self' blob: https://accounts.google.com/gsi/; worker-src 'self' blob:; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'; report-uri /api/csp-report
```

What this stops: any `<script>` that is not a file served by this origin (an injected `<script>`, an `onerror=` / `onclick=`
attribute, `javascript:` URLs, `eval` / `new Function`, scripts from a CDN), loading or posting anything to a foreign host
(`connect-src 'self'`), loading a foreign image (the exfiltration trick above), framing the app (`frame-ancestors`), a hijacked
`<base>` or `<form action>`, plugins, and injected `<style>` elements.

### Exceptions that remain (and why)

| Exception | Why it exists | Why it is acceptable |
|---|---|---|
| `style-src-attr 'unsafe-inline'` (inline `style="..."` attributes) | The UI and the markup it generates set hundreds of `style` attributes (and the CSSOM conversion above produces them). Removing it needs a rewrite of the UI's styling, not a policy change | A style *attribute* cannot run script; `<style>` **elements** stay restricted to this origin, and anything a style can fetch (`url()`) is still limited by `img-src` / `font-src`. Residual risk: cosmetic redressing by injected markup that already got past the sanitiser |
| `img-src` allow-list: `raw.githubusercontent.com`, `github.com`, `avatars` / `user-images` / `camo.githubusercontent.com`, `img.shields.io`, `lh3.googleusercontent.com`, plus `data:` and `blob:` | README badges, GitHub avatars and Google profile photos are shown in answers | Named hosts, not `https:`. `CSP_IMG_EXTRA` adds hosts; `CSP_IMG_ALLOW_ALL=true` restores `https:` (not recommended) |
| `data:` / `blob:` in `img-src`, `media-src`, `frame-src`, `worker-src`; `data:` in `font-src` | Generated charts, previews, downloads and workers are blob/data URLs created by the app itself | Neither scheme can load remote content, and neither can run script (`script-src` is `'self'` only) |
| Classic only: `https://accounts.google.com/gsi/client` (script), `/gsi/style` (style), `/gsi/` (frame, connect) | The original app signs in with Google | Exact paths, not the origin. Google's script injects one inline `<style>` block of its own; that exact block is allowed by hash (`GSI_STYLE_HASH`). If Google changes it the hash stops matching: Chrome's console prints the new hash, add it with `CSP_CLASSIC_STYLE_HASHES`; `CSP_CLASSIC_STYLE_INLINE=true` is the coarse fallback |
| Mermaid's temporary `<style>` (one report per diagram render) | Mermaid builds each diagram's theme CSS as a `<style>` element while measuring; the policy blocks it (no effect) and the app re-applies the same rules through the CSSOM | Not an exception in the policy. The report is expected, counted, and logged at debug level (`csp_violation_known`) |

Removed instead of excepted: `unsafe-eval` (the Classic app's in-page code playground used `eval`; its local fallback now says that
it is blocked and the server sandbox is the supported path - `CSP_CLASSIC_ALLOW_EVAL=true` brings it back for the Classic page only,
never for the main app), `unsafe-inline` for scripts, all CDN hosts, `connect-src` hosts other than this origin (add API hosts you
control with `CSP_CONNECT_EXTRA`).

### Operating it

* Modes: `PRIVACY_CSP=enforce` (the default when `NODE_ENV=production`), `report-only` (same policy, nothing blocked: the default in
  development, because `npm run dev` serves Vite's inline refresh script and hot-reload websocket; also use it to try a change), `off`
  (local debugging only). An unknown value falls back to `enforce`.
* Reports use `report-uri` only. Tested in Chrome: it is delivered immediately; when `report-to` is also present Chrome ignores
  `report-uri` and uses the Reporting API instead, which needs HTTPS and batches for up to a minute. Firefox and Safari only support
  `report-uri`. After a deploy, watch for `"event":"csp_violation"` log lines: each carries the directive, the blocked URL (path only),
  the page, the source file and line, and the first 80 characters of an inline snippet.
* Adding a library: put the files under `web/public/vendor/<name>/`, reference them with a relative `/vendor/...` URL and note the
  version in `web/public/vendor/README.md`. Do **not** add a CDN host to the policy. For a library that injects a `<style>` at run
  time, check `tests/csp.test.ts` (Cytoscape is handled by a stylesheet `<link>` carrying the id the library looks for).
* Never write `onclick="..."` / `onerror="..."` in markup or JS templates; use a `data-act` value handled in
  `web/js/ui/delegated-actions.js` (a test scans the code for inline handlers, `<style>` injection and `eval`).

### What was verified, and what was not

Verified: unit tests (policy shape, env validation, vercel.json sync, report parsing and endpoint limits, the Classic page split,
no inline handlers / injected styles / `eval` / CDN references anywhere in the source); end-to-end checks against the real server;
and a headless Chrome run in enforce mode over every route, the Copilot and Agent pages, the launcher drawer, the Classic app,
rendered markdown, SVG, Mermaid and KaTeX with the converted buttons clicked - 0 violations from the app's own code - together
with attacks that must fail (injected inline script, `onerror`, CDN script, `eval`, `new Function`, `fetch` to a foreign host,

Not verified: a live Vercel deployment (the header values match `csp.ts` by test, but were not served by Vercel), real Google
sign-in with a real account (only that the script loads, its inline style is allowed and the page works), Firefox and Safari
(the CSSOM conversion needs `new CSSStyleSheet()`: Chrome 73+, Safari 16.4+, Firefox 101+; on an older browser an SVG's own
`<style>` is not applied), and the Reporting API path (not used).

## Provider API keys at rest (hardening after the final audit)

The final audit's top remaining risk was that users' provider API keys were plaintext in SQLite and its backups. They are now sealed with the vault
(`server/security/vault.ts`, `secret-store.ts`) whenever `PRIVACY_ENCRYPTION_KEY` is set: AES-256-GCM, a fresh IV per value, bound to the user and model (a value
copied onto another row does not open), also for the Supabase mirror's copy. Reads tolerate legacy plaintext and report a sealed value that cannot be opened as "no key"
(never as ciphertext, never as an exception). A previous key can be configured for rotation. Conversion of existing rows is an explicit operator action
(`SECRETS_MIGRATE`, DEPLOY.md): snapshot first, round-trip check of every value, one transaction, then the write-ahead log is folded in and the file rebuilt so no plaintext stays behind.
Deleting a model blanks the key and `PRAGMA secure_delete` zeroes freed pages. Found while building it, and fixed: a server started **without** the vault key read sealed keys as empty and a model save
wrote that empty value back (silent loss of every sealed key), so an empty key can no longer overwrite a stored one; and `preflight` accepted a vault key of any length >= 32 bytes while the vault needs exactly 32 (it stayed silently off).
**Remaining**: this is opt-in (without `PRIVACY_ENCRYPTION_KEY` keys are still plaintext, and `preflight` warns); the server's own provider keys come from environment variables, not the database; a plaintext copy remains in any backup taken before the conversion; the Supabase path could not be exercised without an account.
Verified: 9 unit tests (a mutation of the save path fails one), preflight tests, and a 20-check end-to-end run on the production build (plaintext, boot migration with snapshot, sealed on disk and in the WAL, models still answer, restart without the key, restart with it, delete).

## Product features added in Task 6 (their attack surface)

Each feature was designed against the same rules as the rest of the API (auth gate first, every query scoped to the caller, foreign ids read as "not found", no secrets in output).

* **Conversation search, tags, folders, pinning, branching** (`server/conversation-library.ts`, `conversation-routes.ts`). Search is a bounded `LIKE` with the wildcards `% _ \` escaped (so `%%` matches nothing, not everything), a 2-100 character query, a cap of 800 matching message rows examined and 50 results; every statement is parameterised and filtered by `user_id`. Tags are limited to 10 per conversation, 24 characters, letters / digits / space / `_` / `-` only (so a tag can never carry markup), and are only ever rendered as text. Branching copies at most 500 messages in one transaction and only from a conversation the caller owns; a message id from another conversation is "not found". Proved by unit tests and a smoke check with three users.
* **Model comparison** (`server/model-compare.ts`, `compare-routes.ts`). The only new endpoint that spends the user's provider quota, so: 2-3 models, an 8,000-character prompt, one comparison in flight per user, 6 per minute (`429` with `Retry-After`), a 60 s timeout per model that cannot hold the others (the call is raced against the abort, so a provider that ignores cancellation is still cut off), and a browser disconnect aborts every upstream request (proved against a hanging provider in the smoke test). Models are looked up by id in the caller's own account; another user's or an unknown id is `404`, a disabled model `409`. Results carry only the model's id, label and provider; error text is scrubbed of that model's key and anything key-shaped (tested with a provider that echoes the Authorization header back). The page renders answers with `textContent`, never as HTML. Nothing is written to a conversation.
* **Accessibility pass.** Not a vulnerability class, but two fixes matter to users who cannot use a mouse: message actions were `visibility: hidden` until hover, which made them unreachable by keyboard, and low-contrast text tokens (the light theme's pastel accent as text was 1.7:1) are now AA.

## Memory (attack surface)

Memory notes are user data that is placed into a model prompt, so: nothing is stored without the user's explicit action; every query is scoped to the owner (another user's id is `404`); notes that look like credentials or e-mail addresses are refused; a note is inserted as a quoted line under a header that says it is data and never overrides the assistant's rules, with newlines and `===` look-alikes stripped so a note cannot fake the block's boundary or start a new "instruction" line; at most 5 notes and 1,200 characters per request; 200 notes per user. This reduces, but cannot eliminate, prompt-injection risk from a note the user wrote themselves (the user controls the content). The privacy export includes the notes and the account erase removes them (the erase also now covers `agent_runs`, which it had missed). Tested end to end, including what the model provider receives.

## Prompt Studio (attack surface)

Prompts are the user's own text, stored per user (every query scoped to the owner, foreign ids are `404`). Prompts that contain credentials are refused before saving; test runs call the user's own models with their own keys through the same guarded runner as the Compare page (a disconnect aborts every upstream request, error text is scrubbed of that model's key, one test at a time, 6 per minute, 8,000 characters after filling, at most 3 calls). Variable values are inserted as text and never re-expanded, so a value cannot inject another variable. Import is validated row by row and capped. Prompts are included in the privacy export and removed with the account. A prompt is not encrypted at rest (it is user content, like a chat message).

## Agent approvals and checkpoints (attack surface)

The approval rule for tools that change saved data is enforced **inside the agent loop** (`server/agent/core.ts`, `policy.ts`), not in the page and not by a request field: a `write` tool always stops the loop before it runs, the request's `approvals` value is validated (anything unknown means the safe default, there is no "off"), a caller that cannot persist an approval request has the call refused, the stateless `/api/agent/run` cannot select a write tool, arguments are validated before approval is even asked, approval ids must match the pending call, and an approval cannot be replayed or used by another user (404). Sessions are scoped to their owner; closing a tab pauses a run rather than leaving it running unseen; goals and conversations are stored (to allow resuming) for 30 days or until deleted, tool outputs are not stored in the audit trail, arguments there are redacted and bounded. The agent still has no shell, filesystem or code-execution tool. Tested including bypass attempts, a real restart mid-run and mutation checks of the gate.

## Account recovery and operator access (attack surface)

Password recovery is where an attacker who does not know a password tries to get one, so every part is built to give them nothing:

* **No enumeration.** `/api/auth/forgot` answers `202` with the same body for known, unknown and disabled addresses and does the mail work after replying (so timing does not differ); it is rate limited per address (3/h) and per IP (20/h) with `Retry-After`. A malformed address is `400` (that reveals nothing about accounts).
* **Tokens.** 32 random bytes (base64url), only the SHA-256 is stored, 30 minutes, single use (an atomic `UPDATE ... WHERE used_at IS NULL AND expires_at > now` must change exactly one row, so two simultaneous attempts cannot both succeed), a new request cancels the older tokens, expired and used rows are purged after a day and removed with the account. The token travels in the URL fragment, which browsers never send to a server or in a `Referer`, and the page removes it from the address bar and history as soon as it has read it. Pages and API answers are `no-store`.
* **A weak or malformed password does not burn the token** (the user can fix a typo); invalid, expired, used and unknown tokens are all the same `400 INVALID_TOKEN`; reset attempts are limited per IP (30/h).
* **Effect of a reset.** All sessions of the account are revoked (memory and database), the sign-in lockout is cleared, the new password goes through the same strength rules and scrypt hashing as sign-up, and a "your password was changed" notice is mailed to the account's address.
* **Mail.** Configured only through environment variables. Addresses and header fields containing line breaks are refused before anything is sent (no header or recipient injection); the SMTP client requires STARTTLS or implicit TLS with certificate verification (plain text only for localhost, and never in production for another host); it refuses to send credentials if STARTTLS is not offered; failures never contain the API key or password. If mail is not configured the server answers `501` instead of pretending.
* **No admin role.** Deliberate: the product has no operation that needs one, and an in-app administrator is a privilege-escalation target. Operator actions (`scripts/admin.mjs`: masked user list, one-time reset link, revoke sessions, disable / enable) need access to the database file, the same boundary that protects the database and the environment. A disabled account is refused at sign-in after the password check (so it does not reveal which addresses exist) and its sessions are removed at once; `disabled_at` is an additive, idempotent column migration.
* **Residual risk.** E-mail account takeover means account takeover (inherent to e-mail recovery); a reset link given by an operator is a bearer credential for 30 minutes; mail delivery was exercised only against local fake servers, not a real provider.

## Known limitations

* Comparison rate limits (and the other in-memory limits) assume one server instance. Search is a substring scan of the caller's messages, newest first, stopping at 800 matching rows (no full-text index: SQLite FTS5 is available but a derived index would hold a second copy of every message, which the privacy export and erase paths would then have to cover).
* The CI workflow first ran on GitHub on 6 November 2026 (pull request #1, run 42118240655): Linux (Node 22 and 24), Windows, macOS and
  the dependency-audit / secret-scan job all passed after two real findings were fixed (three fake test keys flagged by gitleaks; a
  Linux-only test hang caused by project processes without their own process group). It has not run on `main`, and whether its jobs
  are required checks (branch protection) has not been inspected.
* `tsconfig.json` is deliberately non-strict (`strict: false`): "0 errors" means the code type-checks under that setting, not
  that it is strictly typed. A few values are typed `any` or cast where the shape is not known.
* The optional Supabase mirror (`server/rag-routes.ts` -> `syncRagChunkToSupabase`) is passed knowledge-chunk-shaped objects by
  two routes; it cannot be verified without a live Supabase and was only made explicit (`as any` plus a comment), not changed. The
  mirror also stores a pseudonymous placeholder user, never the real e-mail or password hash (that was the effective behaviour all
  along; it is now stated in the code so nobody "fixes" it into a data leak).
* Session lifetime is a fixed 30 days from sign-in (cookie and database row); there is no idle timeout or sliding renewal.
  Sign out, "sign out other sessions" and a password change revoke rows, and revoked/expired rows are now enforced immediately.
* Through the Vercel front door, request bodies over ~4.5 MB are refused by Vercel (project ZIPs are split into 3 MB parts; other
  uploads are single requests and need the API's own address for large files). The Studio chat, document-stream, knowledge Q&A and
  project-generation streams still send their first byte with the first token; behind Vercel a first token slower than 25 s becomes a
  504. The Vercel Edge runtime that `api/proxy.js` uses is deprecated by Vercel; migrating it is untested without an account.
* A cross-tab sign-out race in the web app: when a second tab is still loading while the first signs out, the `storage` event can
  arrive before the second tab knows it is signed in and is ignored (about 1 cold start in 5 in the headless test). The tab
  recovers on its next API call (`401`). Tracked for the final audit.
* Legacy password hashes (plain/MD5/SHA-256) from very old databases can still be *verified* for migration; new
  accounts always use scrypt.
* The SQLite database is not encrypted by the application (use disk encryption).
* In-memory rate limits, build jobs and the agent's concurrency limit assume one instance.
* Uploads no longer sit in memory while they are received, but a handler that needs the whole file (text extraction, ZIP
  extraction, image storage) still loads that one file (up to 100 MB) into memory, and extracted project files are held in
  the server's in-memory project store as before. Peak memory is now about one file per active upload instead of every file.
* JSON / form bodies are limited per route (1 MB default, 25 MB for model requests, 100 MB only for 13 file and export routes: finding #61).
  The 100 MB tier is still large: a signed-in user can make the server buffer up to 100 MB per request on those routes, bounded by the rate limits.
  Lower `JSON_LIMIT_FILES_MB` if your users do not need it. Memory use under many concurrent large requests has not been measured.
* File-signature checks cover the common formats. A hostile file can still be a *valid* file of the claimed type (for example
  a crafted PDF or DOCX aimed at a parser bug); keep the parsing libraries updated (`npm audit`) and consider a virus scanner
  at the edge for public deployments.
* Temp files live under `DARKNESS_UPLOAD_TMP` (default: the system temp folder). On a host with a tiny or read-only temp
  disk, point it somewhere with space; the 100 MB limit times the concurrency caps bounds the worst case (about 1.5 GB).
* Browser sessions are HttpOnly-cookie-only now, but this was verified locally, not against a live Vercel + Render
  deployment. After deploying, confirm sign-in, reload and logout work through the proxy (it forwards `Cookie`,
  `Set-Cookie`, `Origin` and `X-Forwarded-Host`), and set `CORS_ORIGINS` if the site is served from more than one origin.
* The Content-Security-Policy is enforced; the exceptions that remain (inline `style=""` attributes, the image-host allow-list, Google Sign-In on the Classic page) are listed under "Content-Security-Policy". Browsers without constructable stylesheets do not apply an SVG's own `<style>`.
* A configured provider's API key is sent to the provider's URL, which the user chooses. `fetchWithPolicy` scrubs the key from
  error text, but a malicious provider URL still receives it; do not store keys for endpoints you do not trust.
* Rate limits, readiness caching and retry budgets are per process (see "In-memory rate limits" above).
* Running project code (Run & Test) is OFF by default on strict deployments (`ENABLE_RUN_ENGINE`); turning it on lets any
  signed-in user execute commands on the server, so enable it only on a private, single-user instance. The Run & Test tab
  now says so instead of failing silently.
* The shared "global knowledge base" is not reachable in strict mode (it would be visible to every user).
* PDF export uses Roboto (Latin, Cyrillic, Greek); other scripts should use DOCX or HTML.
* Images need a server-side image model; without one the Studio says so and skips illustrations.
